# PromptLab · 提示词工程实验室

> 把 Prompt 工程从「凭感觉调」变成「可拆解、可验证、可复述」的工程流程。

一个纯前端的交互式 Prompt 工程工具集，包含四个核心能力：**可视化构建 Prompt 结构**、**多策略效果对比**、**输出质量量化评估**、**可复用模式沉淀**。

---

## 为什么做这个

在接触 Prompt 工程的实践过程中，我发现一个普遍的断层：

大多数人优化 Prompt 的方式是**盲目重写**——效果不好就换个说法再试一次，缺少可复用的判断依据。结果是经验无法沉淀，换一个任务就要从零开始试错。

但这个流程其实有清晰的输入输出：

- **要素**决定 Prompt 的结构完整性
- **策略**决定任务的能力上限
- **评估**决定迭代的方向

三者缺一，优化就只能靠运气。

PromptLab 把这三点做成可交互的工具，目的不是「替代 ChatGPT」，而是**把隐性经验显性化**——让每一次 Prompt 调整都有依据、有对比、有量化结果。

---

## 核心功能

### 1. Prompt 构建器

左侧是 Prompt 的七大结构要素，每个都可独立开关和编辑；右侧实时渲染完整 Prompt。

每个要素都标注了**它到底在解决什么问题**，而不只是「建议写」：

| 要素 | 解决的问题 |
|---|---|
| 角色设定 | 让模型调用对应领域的知识与语感，而非给出通用答案 |
| 任务定义 | 把模糊动词换成可验收的交付物描述 |
| 上下文输入 | 补齐模型不知道的背景信息，避免它靠猜 |
| 约束条件 | 划定边界：长度、口径、禁用项、必须项 |
| 输出格式 | 让输出可被程序消费，而不只是给人读 |
| 示例引导 | 用样例锚定风格与格式，比形容词描述准确得多 |
| 自检指令 | 把质量校验前移到生成阶段 |

关闭任一要素，右侧会提示「缺少这一项会导致什么后果」——**结构缺失的代价是可见的**。

### 2. 策略对比实验室

对同一任务并行展示四种 Prompt 策略的真实输出与评分：

- **Zero-shot** — 直接提问
- **Few-shot** — 给样例锚定
- **Chain-of-Thought** — 分步推理
- **Structured Output** — 指定 Schema

内置三个典型任务（情感倾向判断、多步推理、信息抽取），每个任务的四种策略输出都附有**逐条点评**，说明差异从何而来、代价是什么。

例如「多步推理」任务中，Zero-shot 因为忽略了「出水管」这个负向条件而算错，CoT 则通过显式确认隐藏前提避开了这个坑——这类差异用文字描述很抽象，并排放在一起就一目了然。

### 3. 输出质量评估

从六个维度对一段 AI 输出打分（权重可调）：

| 维度 | 权重 |
|---|---|
| 准确性 | 25% |
| 完整性 | 20% |
| 低幻觉风险 | 20% |
| 格式合规 | 15% |
| 可执行性 | 12% |
| 风格一致性 | 8% |

默认使用**本地规则引擎**，离线可用，能检出形式层面的问题（JSON 合法性、结构标记、模糊限定词、无依据表述、行动指向缺失等），并定位到具体问题。

同时提供 **LLM-as-a-Judge 评判 Prompt**——在真实生产环境中，把它交给一个强模型，可以得到带理由的语义级评判，成本远低于人工，且评价标准可版本化管理。

### 4. 提示词模式库

沉淀 14 个可复用的 Prompt 模式（思维链、少样本、自我一致性、ReAct、上下文注入、元提示……），每个模式包含：

- **适用场景** — 什么任务该用它
- **模板** — 可直接套用的结构
- **常见坑** — 用错反而变差的情况

### 5. 方法论

把上述实践抽象成一套可复述的框架，包括 Prompt 解剖结构、迭代的六个维度、评估体系、六类常见失败模式与修复方案、以及按任务类型选择策略的决策表。

## 技术实现

- **纯前端，零依赖** — 原生 HTML / CSS / JavaScript，无框架、无构建步骤、无 CDN 依赖
- **离线可用** — 演示数据内置，断网也能完整运行
- **可选接入模型** — 支持 OpenAI 兼容接口，在「接入模型」模式下，评估器会调用真实模型做 LLM-as-a-Judge
- **响应式布局** — 适配桌面与移动端

### 接入模型（可选）

页面右上角切到「接入模型」，填入任意 OpenAI 兼容接口的地址、Key 和模型名即可。提供 OpenAI / DeepSeek / 通义千问 / 智谱 GLM / Moonshot 的一键填入。

配置生效后，「输出质量评估」会把评判 Prompt 发给模型，拿到带理由的结构化评分——也就是 LLM-as-a-Judge 的真实实现，而不只是本地规则。

Key 只保存在浏览器本地存储中，不会上传到任何服务器，也不会随项目一起发布。配置面板内置「测试连接」，可以先验证再保存。

> 部分厂商的接口未开放浏览器跨域（CORS），从网页直连会被浏览器拦截。遇到这种情况，填一个支持 CORS 的中转地址即可。

### 目录结构

```
promptlab/
├── index.html      # 页面结构
├── styles.css      # 样式系统
├── data.js         # 内容资产库（要素定义、场景模板、对比数据、模式库、方法论）
├── app.js          # 交互逻辑与评估引擎
└── README.md
```

把内容与逻辑分离，是因为这个项目里**内容本身就是核心资产**——`data.js` 可以独立迭代，不需要动任何一行交互代码。

### 本地运行

不需要安装任何环境，直接双击 `index.html` 即可。

如需本地服务器：

```bash
python -m http.server 8000
# 或
npx serve .
```

## 设计取舍

**为什么默认用演示数据而不是实时调用模型？**

因为展示的可靠性优先于实时性。在分享、离线或网络不稳的场景下，API 限流和密钥失效都会让展示中断。内置样本保证了**任何环境下都能完整展示产品逻辑**，而实时调用作为可选能力保留——页面右上角切到「接入模型」即可配置。

**为什么评估器用规则引擎而不是直接调模型？**

两者解决的是不同层次的问题。规则引擎负责**形式层面**的检查——JSON 是否合法、结构标记是否存在、有没有模糊限定词。这些用规则做又快又准，且完全可解释。语义层面的判断才需要模型介入。分工明确比「一律丢给模型」更经济，也更可控。
